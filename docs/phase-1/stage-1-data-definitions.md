## 2. PostgreSQL schema

Rendered from the models with the PostgreSQL dialect (this is what migration `0001` will create).

```sql
CREATE TABLE analysis_jobs (
  id UUID NOT NULL,
  repo_url VARCHAR(2048) NOT NULL,
  question TEXT NOT NULL,
  status VARCHAR(9) DEFAULT 'queued' NOT NULL,
  error_code VARCHAR(50),
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now() NOT NULL,
  started_at TIMESTAMP WITH TIME ZONE,
  finished_at TIMESTAMP WITH TIME ZONE,
  CONSTRAINT pk_analysis_jobs PRIMARY KEY (id),
  CONSTRAINT ck_analysis_jobs_job_status
    CHECK (status IN ('queued', 'running', 'completed', 'failed', 'timed_out'))
);
CREATE INDEX ix_analysis_jobs_status_created_at ON analysis_jobs (status, created_at);

CREATE TABLE reports (
  id UUID NOT NULL,
  job_id UUID NOT NULL,
  summary TEXT NOT NULL,
  findings JSONB DEFAULT '[]'::jsonb NOT NULL,
  recommendations JSONB DEFAULT '[]'::jsonb NOT NULL,
  sources JSONB DEFAULT '[]'::jsonb NOT NULL,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now() NOT NULL,
  CONSTRAINT pk_reports PRIMARY KEY (id),
  CONSTRAINT uq_reports_job_id UNIQUE (job_id),
  CONSTRAINT fk_reports_job_id_analysis_jobs
    FOREIGN KEY (job_id) REFERENCES analysis_jobs (id) ON DELETE CASCADE
);

CREATE TABLE execution_events (
  id UUID NOT NULL,
  job_id UUID NOT NULL,
  sequence INTEGER NOT NULL,
  event_type VARCHAR(50) NOT NULL,
  component VARCHAR(50) NOT NULL,
  status VARCHAR(9) NOT NULL,
  duration_ms INTEGER,
  details JSONB DEFAULT '{}'::jsonb NOT NULL,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now() NOT NULL,
  CONSTRAINT pk_execution_events PRIMARY KEY (id),
  CONSTRAINT uq_execution_events_job_id_sequence UNIQUE (job_id, sequence),
  CONSTRAINT fk_execution_events_job_id_analysis_jobs
    FOREIGN KEY (job_id) REFERENCES analysis_jobs (id) ON DELETE CASCADE,
  CONSTRAINT ck_execution_events_event_status
    CHECK (status IN ('started', 'succeeded', 'failed'))
);
```

### Design choices

- **Closed sets get a CHECK constraint, open sets are plain strings.** `status` columns use
  VARCHAR + CHECK (not a native PostgreSQL enum type, which is awkward to alter in migrations).
  `error_code` and `component` will grow in later phases, so they are plain strings validated in
  the application; adding a value needs no migration.
- **UUID primary keys are generated in Python** (`uuid4`), so ids exist before the insert and are
  safe to expose in URLs.
- **Timestamps are timezone-aware and set by the database** (`now()`), so all replicas agree.
- **JSONB contents are validated by Pydantic** (`app.schemas.evidence`) before they are stored;
  the database stores the already-validated shape.
- **Deleting a job deletes its report and events** (`ON DELETE CASCADE`), so no orphans remain.
- **`details` instead of `metadata`** on `execution_events`: SQLAlchemy reserves `metadata`.
- **No secrets, prompts or repository file contents** are stored in any column. Evidence excerpts
  are capped at 1000 characters.

## 3. Alembic migration plan

- Alembic runs with the synchronous psycopg driver; the app uses the async driver. Both use the
  same models and the same database URL built from settings.
- **`0001_initial`:** creates the three tables, constraints and index above. Downgrade drops them
  in reverse dependency order (`execution_events`, `reports`, `analysis_jobs`).
- Revisions are hand-reviewed, not blindly autogenerated: autogenerate produces the draft, then the
  diff is checked against the models before committing.
- Migrations must stay backward compatible with the previous app version (add before remove), per
  Stage 0 section 3b.
- The startup runner (Stage 0 section 3b) applies `upgrade head` under a PostgreSQL advisory lock.

## 5. Configuration shape

Plain settings come from environment variables; secrets come from files named after the field.

| Group | Fields | Secret files |
|---|---|---|
| Mode | `app_env`, `log_level`, `docs_enabled`, `cors_origins`, `trusted_proxy` | |
| PostgreSQL | `database_host`, `database_port`, `database_name`, `database_user`, pool size and overflow, connect timeout, statement timeout, `migration_retry_window_s` | `database_password` (required) |
| Qdrant | `qdrant_url`, `qdrant_collection`, `qdrant_vector_size`, `qdrant_distance` | `qdrant_api_key` (optional) |
| Redis | `redis_url` | `redis_password` (optional in Stage 1; required when Redis is configured, enforced in Stage 4) |
| Request limits | `rate_limit_enabled`, job-create and read limits per minute, `max_request_body_bytes`, `max_repo_url_length`, `request_timeout_s` | |
| Telemetry | `otel_enabled`, `otel_service_name`, `otel_exporter_otlp_endpoint` | |

- Defaults match Stage 0: 5 job creations and 60 reads per minute, 64 KiB request body, 30 s
  timeout, 30 s migration retry window.
- `log_level` and `docs_enabled` default to `None`, meaning "use the mode's default"; the per-mode
  defaults and production safety guards are applied in Stage 4.
- The dev secrets directory is `<repo>/secrets`, resolved from the source file location, not the
  working directory. `SECRETS_DIR` overrides it (applied in Stage 4).
- Settings are frozen once loaded.

## 6. Errors

| Class | HTTP | Code |
|---|---|---|
| `InvalidInputError` | 422 | `validation_error` |
| `NotFoundError` | 404 | `not_found` |
| `PayloadTooLargeError` | 413 | `payload_too_large` |

inputs for `validation_error`.

## 9. Decisions from review

1. **Question:** no minimum or maximum character limit in the schema or the database (`TEXT`).
   The only bound is the request body cap (`max_request_body_bytes`, default 64 KiB), so a
   question cannot be unbounded in practice. An empty question is rejected by a
   non-empty check on the API request model, added in Stage 2 (not a length limit).
2. **`repo_url`:** the cap is the `max_repo_url_length` setting (default 200, enough for any
   GitHub URL of about 160 characters). The column is `VARCHAR(2048)`, so the setting can be
   raised to 2048 without a migration; the setting is rejected above that.
3. **Migration:** no database or migration exists yet; `0001_initial` is written in Stage 4 using
   `VARCHAR(2048)`, so this column size needs no separate migration. A later change to the column
   size would get its own revision.
